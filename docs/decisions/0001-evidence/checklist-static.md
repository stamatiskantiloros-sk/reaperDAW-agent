### Other ReaperMCP facts

**Addressing.**
- Everything is by integer index. Tracks use 0-based `track_index`, with -1 for master where allowed (`get_track`, `reaper_mcp_server.lua:860-872`). Items use a global `item_index`. FX uses `fx_index` and `param_index`. Markers use the enumeration index.
- Indices shift when anything is added or deleted. The code has several fixes for index drift (comment above `find_marker_index`), but it has no GUID scheme at all.
- `track_set_state_chunk` regenerates TRACKID (`:5593-5597`).

**Transport.**
- It is file IPC in `$TMPDIR/reaper_mcp/` (Windows: `%TEMP%`): `command.json` to `response.json`, written to `*.tmp` then renamed (`:21-77`, `send_success` `:327-348`). The Lua side is a `reaper.defer` loop (`main_loop`, `:6207`). Each tick it tries `io.open(command_file)` (`process_command`, `:6132`) and handles one command at most. The tick rate is REAPER's defer rate, roughly every frame.
- The Python client polls the response every 50 ms (`constants.py:65`, `Timeouts.POLL_INTERVAL = 0.05`), takes a cross-process file mutex (`reaper_client.py:131-166`), and sends a request `id` that is echoed back to discard stale replies.
- Heartbeat lock file every 10 s; crash check about every 2 s of polling (`reaper_client.py:398`).
- Expected latency is roughly 50-100 ms per command (unmeasured, inferred from the 50 ms poll plus the defer tick). Default command timeout is 30 s; the long form is up to 600 s.
- Dispatch is single-threaded. A slow command blocks REAPER's UI.

**Gating of dangerous or arbitrary-script commands.**
- There is **no eval or run-arbitrary-Lua command.**
- `script_run` (Python `script_tools.py`, Lua `script.script_run_start` `:5702`) runs only `.lua` / `.eel` files that already exist under REAPER's own `Scripts/` folder. The path must be relative and must not contain `..` (`safe_script_path`, `:5692`). It registers the script as an action and runs it, with no config switch, only a docstring telling the model to confirm with the user.
- `project_main_action` (`:1610`, any action id, no gate) exists in Lua but is **not an exposed MCP tool**. Only `pipeline_tools.py:363` calls it internally (action 40892). The same is true of `fx_add` / `fx_set_param`.
- Tool surface is narrowed with `REAPER_MCP_PROFILE` (full, composition, mixing, analysis, minimal, production) and `REAPER_MCP_INCLUDE_TOOLS` / `EXCLUDE_TOOLS` (`tool_registry.py:78-250`).
- `safety.ensure_backup` saves a timestamped `.rpp` copy once per session before destructive tools.
- Python-side `format_command` only rejects NUL bytes (`protocol.py:7`).
- `path_safety.py` exists for file paths (not read in depth).
- `SECURITY.md` states local-only IPC, with no auth on the IPC directory beyond `chmod 0700`.

### Other Reaper Daemon facts

**Addressing.**
- GUID-first. `find_track` resolves `target_track_guid`, then `target_track_name`, then `track_name_contains`, then index (`:795`). Replies carry track and FX GUIDs ("the stable identity: names can be duplicated and indices shift", `:1645-1647`).
- Track indices in replies are 1-based, with master as 0 (`:704`). FX has both a display index and an `api_index` (input FX carry the 0x1000000 offset).
- Items are addressed by track plus a per-track index.

**Transport.**
- File queue: JSON command files in `inbox/`, replies in `outbox/<id>.json` (`docs/protocol.md`). Publish is by `.tmp` then rename. Commands are processed in filename order.
- The docs say "four times a second", which matches the 0.25 s config default (`poll_interval_seconds`, `:211`). The code is adaptive: when a command was seen in the last 2 s it scans every defer tick, otherwise every 50 ms (`:5530-5538`, unless `adaptive_poll` is false). While playing it handles one command per tick with a 3 ms budget (`:5539-5540`).
- A render blocks the loop, and the heartbeat reports `busy`.
- There is a singleton lock, `reload_bridge`, and a crash recovery triage by `created_at`.

**Gating.**
- Config gates in `bridge_config.json`: `allow_risk_level_3`, `allow_audio_writes`, `allow_project_save`, `allow_preference_writes` and `allow_script_execution`, all default false (`bridge_config.example.json:5-9`).
- `run_script` (`tempo_and_actions.lua:282`) runs agent-supplied Lua. It is off by default, needs `allow_script_execution=true`, does **not** fall back to `allow_risk_level_3`, has a hook-based timeout (default 30 s, max 600 s) and a 64 KiB output cap. Enabling it takes a bridge reload.
- `run_action` runs any REAPER action id. Only save and render actions are gated, and Quit is refused (`ACTION_GATES`, `ACTION_REFUSED`, `:127-141`). So `run_action` is an ungated escape hatch for everything else that REAPER's action list can do.
- Optional shared `auth_token`. `dry_run` is supported on mutating commands.
- The MCP `raw_command` tool (`reaper_mcp.py:2028`) forwards any bridge command type.

## 3. Cross-cutting comparison for the bridge decision

- **Identity.** The Daemon gives GUIDs for tracks and FX and resolves GUID before name before index. ReaperMCP is index-only, and its track/FX/item reads have no GUIDs at all. For any workflow that must survive edits between calls, ReaperMCP needs the GUID additions listed above.
- **Real-unit parameter setting.** Only the Daemon has it (formatted_value bisection). ReaperMCP has normalized-only writes plus a calibration scan.
- **Single-undo batching.** Only the Daemon delivers one Ctrl+Z for many operations. ReaperMCP labels steps and offers `project_undo_group`, but REAPER shows several undo entries.
- **Breadth of reads.** ReaperMCP has the richer item, take and marker reads. The Daemon's read side is thinner (single active take name, no colour, no conversion tools).
- **Gaps in both** (small named handlers in either): fixed lanes (item 5), track move and reparent (3; the Daemon deliberately omits it), beats/seconds conversion (11), project-wide media list (12).
- **Escape hatches.** ReaperMCP has none for arbitrary code, only existing scripts in the Scripts folder. The Daemon has `run_action` (mostly ungated) and a gated `run_script`.
